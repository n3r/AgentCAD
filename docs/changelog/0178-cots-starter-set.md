## Summary

Eight more packages, and the catalog stops being a demonstration. ISO 4014 hex
bolts, ISO 7380-1 button heads, heat-set threaded inserts, DIN 625-1 ball
bearings, 20×20 and 30×30 T-slot extrusions, and NEMA 17 and NEMA 23 motor
outlines — every one with connectors, SPECS on its **interface dimensions**,
docs, presets and a rendered preview, and every one green through the real
publish gate before `agentcad publish` would write its entry. **FR12 is
complete.** The set is also tested as a *kit*: a 608 bearing mounts on a 2020
extrusion through a bracket, two mates, interference-clean.

Writing the first of them found a **live bug**:
`agentcad.toolkit.threads.hex_bolt` imported `HexBolt`, which the pinned
bd_warehouse does not export. Every call had raised `ImportError` since the
helper was written, and nothing in the tree called it, so nothing caught it.

## The bug this slice found

`agentcad/toolkit/threads.py`:

```python
from bd_warehouse.fastener import HexBolt     # does not exist
return HexBolt(size=size, length=length, simple=simple)
```

The pinned bd_warehouse exports `HexHeadScrew` (with `fastener_type` in
`{iso4014, iso4017, din931}`) and **no `HexBolt` at all**, so every call to
`threads.hex_bolt` raised
`ImportError: cannot import name 'HexBolt' from 'bd_warehouse.fastener'`. The
helper has been in the tree since changelog 0023 and is named in
`core/templates.py`'s cheat-sheet and in `docs/part-authoring.md`; nothing
called it, and the toolkit's own test module covered `cap_screw` and not it.
The fix is one import and one constructor, plus a `standard=` argument so
ISO 4017 and DIN 931 are reachable; the two new tests in
`tests/test_threads.py` construct a bolt and assert its ISO 4014 dimensions,
which is the check that was missing.

This is the fifth existing non-test module this plan touches, against a plan
that budgets two. It is reported rather than worked around: the alternative
was for `iso4014` to import `bd_warehouse` directly and leave a documented,
advertised helper broken for the next caller.

## Divergences from the plan, and why

- **The non-fastener packages are interface models, and every README says so
  on its first screen.** A bearing with no balls, an extrusion with no web
  fillets, a motor whose body is a solid block. Each is the geometry a bracket
  has to fit and clear, at the published interface dimensions, and each README
  names what is *not* modelled — because a COTS outline that looks detailed is
  read as detailed. The motor README says in as many words: do not read a
  motor mass off it.
- **`nema17`/`nema23` and `extrusion_2020`/`extrusion_3030` are four packages,
  not two with a `frame` enum.** The plan's file list names four directories
  and FR12 names four entries; more usefully, a project that needs 2020 bar
  should not carry the 3030 profile's dimensions in its lockfile. The two
  extrusion part scripts are the same file with a six-constant profile block
  changed, and that duplication is the price of the separation.
- **The extrusions' slot connectors are rigid, not sliding.** A T-nut does
  slide, but the moving side of a mate must be rigid (the anchor carries the
  DOF), and *where* along the slot a bracket sits is the assembly's decision
  rather than the extrusion's. Stated in the README with the two ways to
  offset.
- **`din625` derives which row it *is* from its own geometry.** The bore check
  looks up the row by the built solid's measured outside diameter and width,
  then compares the bore against that row — so a build that ignored its
  `designation` parameter fails instead of agreeing with itself. A spec that
  reads the same parameter the geometry was built from measures nothing.
- **The bolt-pattern spec finds the holes by radius and measures them at their
  own axes** — so it fails if a hole moves, if one is missing, or if a fifth
  appears. It uses each face's **bounding-box** centre, not `Face.center()`:
  the latter is the parametric centre of the surface, which for a closed
  cylinder sits on the wall (measured: x = −17.0 for a hole whose axis is at
  −15.5, an error of exactly one radius). That cost one red test run and the
  comment is in the code.
- **`thread_insert`'s height spec reads the designation, not a table.**
  `M3-0.5-4.0` is 4.0 mm tall by construction of its own name, so the check
  parses the last field and measures against it. One fewer table to drift.
- **The catalog is not marked `exhaustive`.** The plan says to if the wall
  clock exceeds two minutes. `tests/test_catalog.py` runs 63 tests in 43 s
  with all nine packages through the full nine-stage gate, so `slow` alone is
  right; the threshold is recorded here so a tenth package that crosses it is
  a known decision.

### The fan-out, on the whole catalog this time — 1.40×, below the bar

Changelog 0171 kept the `ThreadPoolExecutor` on **1.55×**, measured on a
synthetic package whose every variant carried a real thread. Changelog 0176
re-measured it on the one shipped package and got **1.08×**. With nine
packages there is enough content to measure it properly, and enough spread to
show why the earlier two numbers disagreed.

Method: one warm-up sweep discarded, then **five interleaved repetitions**
(`1,3 / 3,1 / 1,3 / 3,1 / 1,3`) over all nine packages, so neither setting
takes the cold pass; 3-worker pool, every worker pre-warmed, a fresh cell per
run, `format`+`contract`+`build` only, median per package.

| package | variants | `jobs=1` | `jobs=3` | speedup |
|---|---|---|---|---|
| din625 | 14 | 0.68 s | 0.47 s | 1.45× |
| extrusion_2020 | 7 | 0.65 s | 0.27 s | 2.38× |
| extrusion_3030 | 7 | 0.64 s | 0.26 s | 2.46× |
| iso4014 | 17 | 3.82 s | 3.13 s | 1.22× |
| iso4762 | 20 | 6.08 s | 3.38 s | 1.80× |
| iso7380 | 17 | 2.95 s | 2.47 s | 1.20× |
| nema17 | 6 | 0.33 s | 0.23 s | 1.39× |
| nema23 | 6 | 0.32 s | 0.23 s | 1.39× |
| thread_insert | 13 | 12.79 s | 9.91 s | 1.29× |
| **whole catalog** | **107** | **28.34 s** | **20.30 s** | **1.40×** |

Per-repetition totals, which is what says the number is stable:
`jobs=1` [28.34, 28.08, 28.54, 28.24, 28.42], `jobs=3` [20.22, 20.82, 21.87,
20.09, 20.30].

**The plan's own rule is "under 1.5× on a 3-worker pool, delete the
ThreadPoolExecutor and ship the gate serial." On the catalog the product
actually ships, the fan-out earns 1.40× — it does not clear that bar.**

Two things behind the number, both measured rather than argued:

- **Only about half of the build stage is inside the kernel.** Instrumenting
  `service.kernel.request` during a `jobs=1` run of `iso4762` (changelog
  0176): of 5.85 s, **2.59 s (44%)** is inside `build` calls and **3.26 s** is
  per-variant work in the server process — `store.get_part`, the cache key,
  the metrics sidecar, the status slot. Amdahl's ceiling for three workers
  over a 44% parallel fraction is 1.42×, which is almost exactly what the
  catalog measures. The kernel side parallelises fine: the same 20 builds
  issued straight at the pool take 1.10 s serial and 0.22 s across three
  threads.
- **The per-package spread is 1.20×–2.46×, and it tracks build *evenness*,
  not build cost.** The extrusions (seven identical-cost variants) reach
  2.4×; `thread_insert` and `iso4014` (one expensive real-thread variant
  among a dozen cheap ones) sit at 1.2×, because `KernelPool._pick` routes by
  `hash(affinity) % size` and one long build on one worker sets the wall
  clock. That is also why the single-package numbers in 0171 and 0176
  disagreed so widely; a one-package measurement of this is not a
  measurement.

**The decision is not taken here, and that is deliberate.** Deleting the
executor is a change to slice 5's shipped, tested behaviour (`--jobs` on two
CLI commands, `jobs` on the `validate_package` tool, and
`test_jobs_one_and_jobs_four_produce_identical_reports`) on a 0.1× margin, in
the last slice of a content sequence. What this slice owes is the number, and
the number is now on the whole catalog with its variance. If it is deleted,
the report is byte-identical — `jobs=1` is a first-class path and the test
that pins the two agreeing row for row is what makes the removal safe.

## Notes

- **Two size vocabularies, three now.** PRD-010's hole standards name a thread
  `"M5"`; bd_warehouse fasteners name it `"M5-0.8"`; a ruthex heat-set insert
  names it `"M3-0.5-4.0"` (thread-pitch-height). Each package's README says
  which one its `size` enum speaks.
- **The interoperability test is the FR12 claim.** Nine packages that each
  pass a gate are nine packages; a bearing that mounts on an extrusion through
  a bracket, with both mates resolving off connectors two separately authored
  packages declared and a clean interference check, is a **kit**. The test
  asserts the two resolved positions, not merely the absence of an error.
